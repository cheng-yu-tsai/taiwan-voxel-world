# 技術、效能與素材流程建議

這份路線圖描述現有瀏覽器原型如何逐步擴充，不預先決定正式版平台或引擎。效能門檻均為建議測量目標，尚未在實際裝置上驗證。

## 現況

- 瀏覽器使用 Three.js ES modules，透過 `site/index.html` 的 import map 固定 CDN 版本；GitHub Pages 直接發佈靜態檔案，沒有打包步驟。
- `config.js`、`terrain.js`、`island-geometry.js`、`chunk-index.js`、`world.js`、`player.js`、`ui.js` 與 `main.js` 分工管理地形、世界和介面。
- 方塊網格依水平區塊合併；修改方塊後只重建受影響區塊及邊界鄰區。
- 測試以 Node 內建測試執行，適合設定、地形、幾何、索引和存檔驗證。Three.js 場景目前沒有自動瀏覽器端到端測試。
- GitHub Actions 在 Pages 部署前以 Node.js 24 執行完整 Node 測試套件，並對整體行／分支／函式覆蓋率設 80% 下限；測試工作只需讀取 repository，Pages 發布權限僅授予後續部署工作。
- `site/benchmark.html` 可在瀏覽器量測初始世界生成、單區塊網格重建、合成世界網格及 3 秒畫面更新；畫面更新記錄平均 FPS、`requestAnimationFrame` 間隔分布，並在支援的瀏覽器回報 Long Animation Frames 與耗時腳本；量測工具不讀寫遊戲存檔。
- 遊戲使用 Three.js `Timer` 搭配頁面能見度處理時間步長，陰影使用現行 `PCFShadowMap`。
- 方塊材質目前是程式化純色；尚未建立外部模型、貼圖或音效資產管線。
- 世界存檔目前使用 localStorage。JSON 備份上限 32 MB 是解析器限制，不代表瀏覽器能將同等大小存進 localStorage；容量不足時匯入會失敗並保留目前世界。

## 建議分階段

### A. 完成小型可玩原型

- 延續 Three.js、ES modules 與 GitHub Pages，避免在尚無平台需求前重寫引擎或加入建置系統。
- 新增玩法邏輯時優先抽成不依賴 WebGL 的純模組，使用 Node 測試可重現的規則。
- 以代表性島嶼和常見裝置驗證移動、建造、存檔與觸控流程；遇到場景／輸入整合問題時再補瀏覽器自動化。

### B. 建立可追溯的素材流程

- 需要自訂立體物件時，優先用 Blender 製作並匯出 glTF Binary（`.glb`），透過獨立載入模組加入 Three.js 場景。
- 每項外部模型、貼圖或音效記錄來源、作者、授權和修改內容；避免將來源資訊只留在檔名或聊天紀錄。
- 先以少量代表性資產建立載入與授權流程，再依實際載入時間和記憶體觀察決定貼圖格式、壓縮及細節層級。
- 保留程式化色塊作為缺少資產時的回退樣式，並使用穩定的方塊／物件 ID 對應資產，避免以顯示名稱當資料鍵。

### C. 量測後再處理世界規模

- 使用 `site/benchmark.html` 的固定場景：初始地圖、額外 5,000 方塊、選擇性 20,000 方塊，以及集中於單一區塊的 2,000 方塊壓力情境。
- 建議在桌面與一台中階行動裝置記錄世界生成時間、編輯後網格重建時間、記憶體、平均 FPS 和畫面更新間隔 P95；先取得基準，再決定是否需要更小區塊、視距調整或背景生成。
- 初始生成採一次暖機後的三次中位數；單區塊指標只量網格重建，不含放置／挖除及索引更新。頁面進入背景時會略過 FPS 結果。
- 畫面間隔是瀏覽器提供的 `requestAnimationFrame` 呼叫間距，不是 GPU 呈現完成時間；需連同裝置、視窗大小和其他環境資訊判讀，不能單靠 P95 推算完整輸入延遲。
- 目前已按區塊索引縮小局部重建範圍；在量測證明瓶頸前，不先引入多執行緒或更複雜的地形快取。

### D. 在持久化需求增加時擴充儲存

- 小型單人世界可先使用 localStorage；當實際存檔接近瀏覽器配額，或同步序列化影響互動時，改評估 IndexedDB 非同步儲存。
- 若改用 IndexedDB，需先明確處理讀寫失敗、存檔版本升級、備份匯出及重設流程，再變更儲存層；不要只提高 JSON 檔案上限。
- 只有在多人同步、雲端跨裝置或帳號功能確定進入範圍時，再設計伺服器與驗證機制。

## 桌面效能基準（2026-11-26）

公開 GitHub Pages 版以 Chrome 158、Windows x64、1280×720 視窗、device pixel ratio 1.25、瀏覽器回報 8 GB 裝置記憶體，執行一次標準量測：

| 情境 | 方塊數 | 觀察值 |
| --- | ---: | --- |
| 初始世界生成與網格（三次中位數） | 5,410 | 33.8 ms（範圍 28.4–40.8 ms） |
| 單一區塊重建（十次中位數） | 5,410 | 2.3 ms |
| 加 5,000 個分散方塊 | 10,410 | 77.5 ms |
| 單一區塊加 2,000 個分層方塊 | 7,410 | 45.4 ms |
| 畫面更新（3 秒） | 5,410 | 平均 54.8 FPS；間隔 P50 17.5 ms、P95 18.4 ms、最大 108.2 ms |

這是一個桌面瀏覽器的一次觀察，不代表裝置群體表現。當次最大 `requestAnimationFrame` 間隔高於 100 ms，但平均和 P95 尚可；間隔數值本身無法指出是哪個腳本或繪製階段造成。新增的量測診斷可在支援時回報長影格中的腳本耗時，否則需重跑或用瀏覽器效能追蹤。目前沒有中階手機數據，也沒有依這筆結果安排引擎最佳化。

同一桌面瀏覽器在加入診斷後的第二次 3 秒畫面更新為平均 55.9 FPS、rAF 間隔 P50 17.7 ms／P95 18.4 ms／最大 53.5 ms；Long Animation Frames API 記錄 3 個長影格、最長 116.8 ms，腳本總耗時 198.5 ms，其中量測頁自己的 `benchmark.js` 共 58.0 ms。rAF 間隔與 LoAF 影格時長定義不同，不能互相替代；這個腳本歸因屬於量測頁的執行結果，不等同已定位遊戲主頁的瓶頸。

### 更新後的本機工作樹量測（2026-11-26）

為確認量測世界與目前新世界內容一致，在 `http://127.0.0.1:8765/benchmark.html` 以 Windows x64、Chrome 158、1280×720、device pixel ratio 1.25 的可見分頁執行一次標準量測。瀏覽器回報 8 GB 裝置記憶體、JavaScript heap 19.2 MB、WebGL 可用；Long Animation Frames API 可用，頁面能見度為 visible，20,000 方塊選項未開啟。

| 情境 | 方塊數 | 觀察值 |
| --- | ---: | --- |
| 初始世界生成與網格（三次中位數） | 5,440 | 63.7 ms（範圍 55.4–70.3 ms） |
| 單一區塊重建（十次中位數） | 5,440 | 4.1 ms（區塊 -1,0） |
| 加 5,000 個分散方塊 | 10,440 | 72.4 ms（49 個區塊） |
| 單一區塊加 2,000 個分層方塊 | 7,440 | 37.8 ms（17 個區塊） |
| 畫面更新（3 秒） | 5,440 | 平均 1.6 FPS；rAF 間隔 P50 1,010.7 ms、P95 1,015.0 ms、最大 1,015.0 ms；LoAF 0 次 |

新增離島內容後的世界比先前公開版基準多 30 格，已由共用生成入口納入測試。這次畫面更新結果與先前桌面量測差異很大，雖然分頁標示可見、LoAF API 可用，但沒有收集到長影格，因此尚無法定位原因；單次 localhost 測量不應當作發布版表現或直接推導為遊戲主迴圈瓶頸。推薦先以前景桌面分頁重跑確認，再用已部署的同一版本在手機重跑，依可重現結果安排效能工作。

在同一個本機分頁以相同設定重跑後，初始生成為 36.9 ms、單區塊重建 3.0 ms、5,000 分散方塊 127.2 ms、2,000 集中方塊 36.9 ms；畫面更新平均 1.0 FPS，rAF 間隔 P50 1,012.5 ms／P95 1,014.0 ms，偵測到一個 935.3 ms 長影格，但沒有可歸因腳本。極低更新率在兩次本機執行都出現，其他計時則有變化；目前仍需用完整桌面瀏覽器的前景分頁複測，才能區分應用程式內瀏覽器執行環境、裝置當下負載或遊戲／量測頁因素。

另外由 Codex 的 Chrome 連線建立本機量測分頁，視窗尺寸 1536×730、device pixel ratio 1.25；瀏覽器回報 8 GB 裝置記憶體、WebGL 可用及頁面能見度 visible。兩次畫面更新分別為 2.2 FPS（rAF P50 564.4 ms／P95 1,011.0 ms，1 個 203.7 ms 長影格，腳本累計 198.4 ms 但來源 URL 空白）和 1.0 FPS（P50 1,011.4 ms／P95 1,013.3 ms，無長影格）。Chrome 連線不支援可見度控制，無法確認該分頁在作業系統層級是否真的位於前景，因此這仍不能替代使用者可見的完整桌面分頁測試，也不能定位約一秒的 rAF 間隔原因。

加入新的診斷欄位後，另一次 Chrome 158 本機量測記錄 `visibility-state` 初始與目前狀態皆為 visible、renderer 字串 `WebKit WebGL`。該次 3 秒畫面更新為 2.3 FPS，rAF 間隔 P95 1,009.1 ms；`renderer.render()` JavaScript 呼叫耗時 P50 1.4 ms、P95／最大 46.1 ms；LoAF 最長 236.1 ms、腳本累計 234.4 ms。render() 計時不包含 GPU 完成時間，但它遠低於 rAF 間隔，不能單靠加速遊戲網格或減少這個呼叫來解釋約一秒的停頓。初始可見度紀錄亦只描述頁面能見度，不證明作業系統視窗取得焦點；效能原因仍未定位。

再把街角座椅和綠島岸礁納入共用世界生成後，本機效能頁確認世界為 5,453 格：初始生成 30.1 ms、單區塊重建 2.1 ms、5,000 分散方塊 121.6 ms、2,000 集中方塊 39.9 ms。該分頁 3 秒畫面更新為 1.6 FPS、rAF P95 1,009.8 ms、render() CPU P95 44.7 ms，LoAF 0 次；一筆應用程式內瀏覽器觀察仍不足以定位效能問題。

## 暫定效能目標

開始測量後，可先以以下目標作為討論基準，而非已達成的承諾：初始世界在中階行動裝置 3 秒內可操作、常見編輯的重建時間低於 50 毫秒、穩定遊玩接近 30 FPS。未完成實機量測前，不應把這些數字寫成現況或發布保證。

## 下一個技術檢查點

桌面基準已記錄；下一步在使用者可見的完整桌面瀏覽器前景分頁重跑目前 localhost 量測，再在一台中階手機開啟 [效能量測頁](../site/benchmark.html)，用相同設定重跑並記錄瀏覽器與裝置。現有 Chrome 連線無法確認作業系統層級的分頁前景狀態，因此先保留此待辦。支援的瀏覽器會在量測報告中列出長影格與腳本耗時；若間隔仍未解釋，再用完整瀏覽器效能追蹤調查。若只能使用桌面瀏覽器，保留限制，不推論行動裝置表現。
